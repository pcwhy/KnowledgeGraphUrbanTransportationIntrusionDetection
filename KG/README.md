# KG Transportation System

This repository contains the active code and cached inputs for a
transportation-cybersecurity research pipeline. Structured outputs are
generated locally when you run the experiments. The project compares
three detector families:

- a local-rule baseline,
- a flat-feature logistic detector,
- and a knowledge-graph detector with explicit transportation-state reasoning.

The GitHub export intentionally excludes local-only material such as
`archive/`, `.venv/`, `.cache/`, and the private export staging folder
`ToGithub/`.

## What Is In This Repository

The repository follows a three-layer workflow:

1. `raw_data/`
   - cached external inputs used by the experiments
2. `experiments/`
   - code that runs the synthetic, city-scale, and overhead studies
3. `results/structured/`
   - machine-readable outputs generated by the experiments

## Quick Start

### 1. Create a Python environment

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
```

### 2. Install the project dependencies

This repository does not currently ship a pinned `requirements.txt`, so install
the packages used by the experiment code directly:

```bash
python -m pip install matplotlib networkx numpy osmnx pandas scikit-learn shapely geopandas
```

If your platform needs extra geospatial dependencies, install them before
`osmnx`, `geopandas`, or `shapely`.

### 3. Run an experiment

Synthetic controlled study:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/synthetic/run_experiments.py
```

Real-city case study:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/city/real_city_case_study.py
```

Real-city benchmark:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/city/real_city_benchmark.py
```

Overhead benchmark:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/analysis/benchmark_overhead.py
```

KG snapshot export:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/analysis/export_kg_tikz.py
```

## Data Acquisition

### OpenStreetMap road graphs

The drivable road-network graphs used by the city experiments are derived from
OpenStreetMap. In the current workflow, they are cached locally as GraphML
files in `raw_data/city_cache/`.

For a new city, the expected output is:

- `<city>_drive.graphml`

You can generate this input with `osmnx` by downloading the drivable network
for the target city and saving it to GraphML. The benchmark code expects a
drive-network graph rather than a pedestrian or all-mode graph.

### AADT and permanent-count-station layers

The current Texas-city pipeline uses TxDOT data for:

- Annual Average Daily Traffic (AADT)
- permanent-count-station coverage

In this repository, those inputs are already cached as GeoJSON files in
`raw_data/city_cache/`.

The expected filenames are:

- `<city>_txdot_aadt.geojson`
- `<city>_txdot_permanent_count_stations.geojson`

If you are porting the pipeline to a new Texas city, fetch the raw source data
from the relevant TxDOT public GIS or traffic-data portal, then export or
convert the layers into GeoJSON before placing them in `raw_data/city_cache/`.

If you are porting the pipeline outside Texas, use an equivalent traffic-volume
dataset and an equivalent monitored-station dataset, then normalize their
columns to the fields expected by the city benchmark code.

### Expected cache convention

Each city should contribute one consistent filename prefix across all cached
inputs. For example:

- `austin_drive.graphml`
- `austin_txdot_aadt.geojson`
- `austin_txdot_permanent_count_stations.geojson`

Using a stable prefix is the easiest way to wire a new city into the benchmark
configuration.

### `experiments/common/`

- `project_paths.py`

### `experiments/synthetic/`

Controlled full-coverage experiment code:

- `logistic_feature_importance.csv`
  - flat-feature coefficient summary
- `results.json`
  - structured aggregate output for downstream inspection

### `experiments/city/`

Real-city experiment code for Austin, Houston, and Dallas:

- `real_city_case_study.py`

  - structured benchmark output
- `city_transfer.csv`

- `city_logistic_feature_importance.csv`

Maintenance and overhead analysis:

Main outputs written after the analysis scripts run:

- `results/structured/overhead/overhead_results.json`

## Current Benchmark Settings

The current city-evaluation configuration is:

- `10 x 10` zoning
- route-library cap `800`
- `500` vehicles per episode
- `8` episodes per attack family
- `20/12` train-test split
- `2.0%` attacker share

The current benchmark code lives in:

- `experiments/city/real_city_benchmark.py`
- `experiments/synthetic/urban_transport_kg_ids.py`

## How To Port The Pipeline To Another City

If you want to adapt the real-city pipeline to a new city, use the workflow
below.

### 1. Prepare the city inputs

The current city pipeline expects three core inputs for each city:

- a drivable road graph in GraphML format
- an AADT layer in GeoJSON format
- a permanent-count-station layer in GeoJSON format

Store the new files in `raw_data/city_cache/` using a consistent city prefix.
The existing examples are:

- `austin_drive.graphml`
- `austin_txdot_aadt.geojson`
- `austin_txdot_permanent_count_stations.geojson`

Follow the same pattern for the new city.

### 2. Register the city in the benchmark code

The main city configuration logic lives in:

- `experiments/city/real_city_benchmark.py`
- `experiments/city/real_city_case_study.py`

Add the new city to the city-configuration structures in those files, including:

- the display name
- the file paths for the road graph and sensor layers
- any city-specific geographic bounds or preprocessing hooks

If you are using a non-TxDOT source, make sure the loaded columns are mapped
into the fields expected by the benchmark code before running the pipeline.

### 3. Verify the sensing and coverage assumptions

Before trusting the results, confirm that the new inputs support the same basic
signals used by the current pipeline:

- road-segment topology
- traffic volume observations
- monitored intersections or count-station proxies

The KG detector and flat-feature detector both depend on these derived city
features. If the new city has much sparser sensing coverage, expect the real-city
results to shift.

### 4. Run the descriptive city pass first

Start with:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/city/real_city_case_study.py
```

Then inspect:

- `results/structured/city/real_city_case_summary.csv`
- `results/structured/city/real_city_configuration.csv`

This is the fastest way to confirm that the city graph, coverage counts, and
configuration values look sensible before you launch the full benchmark.

### 5. Run the full city benchmark

After the city-case outputs look correct, run:

```bash
MPLCONFIGDIR="$PWD/.mplconfig" XDG_CACHE_HOME="$PWD/.cache" \
  .venv/bin/python experiments/city/real_city_benchmark.py
```

Then inspect:

- `results/structured/city/real_city_benchmark.csv`
- `results/structured/city/city_transfer.csv`
- `results/structured/city/city_logistic_feature_importance.csv`

### Practical Notes

- Keep the city filename prefix consistent across all input files.
- Add one city at a time and verify the case-study outputs before expanding the
  benchmark set.
- If your city uses different sensor schemas, normalize them at the ingestion
  point instead of scattering one-off fixes across the detector code.
- The quickest places to debug a failed port are
  `experiments/city/real_city_case_study.py`,
  `experiments/city/real_city_benchmark.py`, and
  `experiments/common/detection_shared.py`.
